# Разработка на готовой базе

Это готовый Flutter + FastAPI шаблон. Выполняй пользовательскую задачу напрямую,
переиспользуя существующий код. Не начинай проектирование приложения заново.

## Рабочий порядок

- Для понятной задачи сразу переходи к реализации. План, бриф, карта экранов,
  истории и карточки функций не являются предварительными условиями.
- Для текста, цвета, отступа и локальной правки виджета читай только нужный
  файл и используемые токены/ARB. Не загружай архитектурные helpers и backend.
- Для новой фичи читай ближайший аналог: `category` во Flutter и `categories`
  в API. Загружай только нужный helper; уже прочитанные правила не перечитывай.
- Выполняй весь согласованный объём. Не останавливайся после каждой фичи ради
  формальной приёмки и не запускай следующий скилл только из-за его номера.
- Обычные технические решения принимай самостоятельно. Уточняй только то,
  что действительно блокирует реализацию; небольшие допущения сообщай кратко.
- Не создавай `artifacts/`, отчёты, очереди, планы и другие документы, если
  пользователь не попросил сохранить результат в файл. Существующие документы
  используй по необходимости; отсутствие документа не блокирует работу.

## Одна структура для всех фич

Размещай код в существующих каталогах. Не вводи параллельную архитектуру
`features/<feature>/data/domain` рядом с общей `lib/data`.

Flutter:

```text
lib/data/models/request/<feature>_request.dart
lib/data/models/response/<feature>_response.dart
lib/data/datasources/remote/api_service.dart
lib/data/repositories/<feature>_repository.dart
lib/features/<feature>/presentation/pages/       # экран и bloc рядом с ним
lib/features/<feature>/presentation/widgets/     # только нужные виджеты
```

Поток новой фичи: `page → BLoC → конкретный repository → ApiService`.
Один repository объединяет операции фичи. BLoC может создавать типизированный
request и хранить response-модель. Ошибки проходят через существующие
`ErrorHandler`, `Failure` и `Either`. DI — ручные регистрации GetIt в
`core/di/di.dart`: repository через `registerLazySingleton`, BLoC через
`registerFactory`. Сохраняй вызовы `init()` сервисов и восстановление сессии
до запуска приложения. Маршруты — `app/app_router.dart`, строки — `lib/l10n/*.arb`.

Не добавляй interface + implementation, use case на каждый запрос, DTO-копию
response и mapper между одинаковыми полями. Дополнительный слой нужен только
для конкретной сложности задачи. Категории — рабочий образец прямого потока
без этих обёрток. В готовых auth/profile они пока есть: при обычной доработке
сохраняй совместимость; не копируй их слои в новые фичи.

FastAPI:

```text
app/models/<feature>.py
app/schemas/<feature>.py
app/repositories/<feature>_repository.py
app/services/<feature>_service.py
app/api/v1/<feature>.py
```

Переиспользуй `BaseRepository`; дополнительные запросы — в repository,
правила — в service, HTTP — в route. Сохраняй простой способ сборки базы:
`Service(db)` создаёт конкретный `Repository(db)`. Подключай dependency в
`core/dependencies.py`, router в `api/v1/router.py`. Новая таблица требует model
и Alembic migration; при изменении только UI эти файлы не нужны. Не создавай
пустые слои, фабрики, интерфейсы или отдельную DI-систему ради тестирования.
Зависимости Python описывай только в `init-api/requirements.txt`;
`pyproject.toml` и Docker используют этот же список.

## UI/UX в init-app: mobile и web вместе

- Любая UI/UX-фича или правка в `init-app` по умолчанию реализуется для
  Android/iOS и Flutter Web в той же задаче. Не откладывай web-компоновку на
  отдельный этап. Ограничение одной платформой допустимо по прямому запросу.
- Используй общие маршруты, BLoC, данные и компоненты. Меняй только компоновку
  через `AppLayoutItemBuilder`: narrow ≤ 550, wide > 550 логических пикселей.
  Ширину определяй по окну, а не через `kIsWeb`: узкий браузер тоже narrow.
  Не создавай две независимые реализации одной фичи.
- На narrow сохраняй удобные touch-цели, SafeArea, прокрутку и видимость полей
  при экранной клавиатуре. На wide используй доступное место и ограничивай
  ширину форм/текста; поддерживай мышь, Tab-фокус и клавиатурные действия.
  Существенные действия должны быть доступны и без hover.
- При изменении размера окна сохраняй введённые данные, состояние и текущий
  маршрут. Не создавай BLoC и контроллеры заново при переключении компоновки.
  Подключай новый экран к существующей узкой и широкой навигации, если он должен
  быть доступен из меню; сохраняй переходы и возврат в приложении и браузере.
- В общем коде используй API и зависимости с поддержкой mobile и web.
  Платформенные возможности изолируй; не импортируй `dart:io` в общие UI-файлы
  и не используй `Platform.is...` для выбора размера интерфейса.
- При просмотре diff учитывай обе компоновки затронутого сценария: доступность
  действий, состояния загрузки/ошибки, переполнение и платформенные вызовы.
  Это часть реализации, без отдельного отчёта и обязательных запусков. Если
  приложение не запускалось, не называй UI визуально проверенным. Правила
  запуска, сборки и деплоя остаются в разделе ниже.

## Что сохранять

- Согласованный Flutter/FastAPI контракт: `/api/v1`, JSON-поля, nullable-типы,
  пагинация, формат ошибок и Bearer auth.
- Проверку владельца данных на backend, валидацию ввода и атомарность операций.
  Для изменения БД — новую миграцию, без переписывания применённых миграций.
- Готовые session, router, theme, localization, UI-kit и инфраструктуру.
- Секреты только в локальном env или настройках хостинга, никогда в git и отчётах.

## Минимум сопутствующей работы

- По умолчанию реализуй реальный API-контракт. Не создавай и не обновляй моки,
  fixtures, fake-серверы, demo-данные и тесты без прямого запроса пользователя.
  В шаблоне нет mock-режима: приложение использует реальный API.
- Не запускай приложение, браузер, эмулятор, Docker, анализаторы, тесты и сборки
  без запроса. Запрошенный запуск выполняй без повторного запроса разрешения.
- Генерацию выполняй только когда меняются её входы: ARB → `flutter gen-l10n`;
  Retrofit/JSON/assets → один запуск build_runner после всех правок.
  Для DI, BLoC и обычной правки виджета генерация не нужна. Generated-файлы
  вручную не правь.
- Просмотри изменённый diff, импорты и затронутый контракт. Не превращай это
  в полный аудит проекта. Кратко сообщи результат и фактически выполненные проверки.
- Деплой — только по запросу. Покупки и создание платных ресурсов требуют
  согласования конкретной стоимости; уже полученное согласие не запрашивай повторно.
